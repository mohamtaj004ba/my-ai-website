# Google Workspace read preparation — not connected or operational

This small boundary extends the existing Agent Operations integration architecture; it creates no route, journal, credential accessor, registry entry or permission grant. The current OAuth record `credential-recorded-unconfirmed` remains unusable. No module imports this preparation into operational execution. Work-connected applications are not inherited.

`agent-operations-google-workspace-read.js` requires explicit trusted authorization and transport callbacks, with no default network implementation. Offline fixtures exercise those boundaries without accessing Google or credentials. A future trusted gateway must authorize before and after each read using the same authoritative subject, owner/workspace, task, source commit, exact deployment ID and origin, release, connection revision, resource allowlists and short expiry. Model input cannot supply credentials or authority. This snapshot is a future gateway contract, not a new authorization system or promotion of existing OAuth state.

Prepared operations are limited to:

- Calendar: one explicitly approved calendar, an approved interval of at most 24 hours, ten events maximum. Return hashed event IDs, status and dates/times only. No titles, descriptions, attendees, locations, links or pagination follow-up.
- Drive: one explicitly approved file ID, metadata only: coarse MIME category, size, modification time and trashed state. No account search, file names, content, export, owners, permissions or download links.
- People: one explicitly approved person resource, deletion flag and enumerated source types only. No address-book listing, names, email addresses, biographies, photos or contact content. `people/me` is denied.

Fixed GET endpoints, redirect denial, JSON MIME, 32 KB streamed response bound, three-second whole-operation deadline, cancellation, exact resource binding and pre/post authority equality are enforced. Unknown fields in provider bodies are discarded; raw provider errors are not returned. Calendar/Drive provider timestamps are validated against real calendar components and normalized to UTC. Timed event intervals must be ordered and overlap the approved window. All-day dates remain ordered calendar-local dates with explicitly unverified overlap because calendar timezone is unavailable; they do not establish UTC times or proven window overlap. Mixed date/dateTime endpoints are rejected. Missing cancelled-event dates remain explicitly unavailable. Distinct observation and complete prepared-receipt hashes bind the immutable projection and task/resource context; these are integrity checks, not a signature or independent authority. No refresh, retry, writes, paid model dispatch, recurring work or publication exists.

Operational prerequisites remain deliberately unmet: an independently reviewed confirmation policy for the existing encrypted OAuth record; owner-selected exact resources/time window and task grant; gateway-only credential delivery and existing cancellation/revocation integration; atomic authorization/audit persistence in the current ledger; release fingerprint coverage; independent security review; separately authorized harmless real-provider verification. No credentials should be provisioned or exposed to test this preparation. Docs/Sheets content and Gmail remain unsupported and outside this increment.

Official contracts checked: [Calendar events.list](https://developers.google.com/calendar/api/v3/reference/events/list), [Drive partial fields](https://developers.google.com/workspace/drive/api/guides/fields-parameter), [People get](https://developers.google.com/people/api/rest/v1/people/get). Provider metadata projection is intentionally much narrower than these APIs. Offline success is not evidence of consent, actual Google account access, live compatibility or operational readiness.
