## Trusted reviewer attestation

The existing Preview API exposes owner-only organization-review-read and organization-review-attest. Every action uses existing session, administrator membership, workspace ownership and same-origin checks; the review policy rechecks identity and ownership. Worker credentials and model capabilities cannot use this route. No separate login, credential or operational grant was added.

Reviews use the same Redis CAS document and hash-linked audit log, in a bounded append-only collection. Bindings include original task/revision, scope/source, execution runtime where retained, original release, image hashes, findings, blind seal, QA verdicts, original acceptance and Chief report, plus the current review-surface source/deployment/fingerprint. New tasks retain server-derived workspace/runtime metadata; unknown historical workspace/implementer identity is explicitly unknown, never invented.

Known self-implementer review is denied. Historical reviewer independence remains unverified unless actual implementer identities and an independent server policy establish it. Authentication alone does not prove human inspection. The owner UI requires four locally selected original PNGs, checks SHA-256 and dimensions, and displays them without uploading bytes. Submitted hashes remain a declaration: a direct authorized API client already knows them. No cryptographic proof of human visual inspection is claimed.

Individual owner judgments are separate from immutable QA dispositions. Every record has reviewer identity hash/role, workspace hash, timestamps, exact evidence binding and qualified inspection basis. **Owner review records always have acceptedWork=false and operationalAuthority=false.** They cannot rewrite historical acceptance, resurrect a task, grant paid permission or bypass independent QA. Introducing an independently authorized acceptance policy remains a separate limitation, not a hidden automatic promotion.

Identical uncertain-delivery replay returns the original record; altered keys/payloads, stale state, tampered evidence, known self-review and concurrent active execution fail closed. The UI preserves a pending submission key/payload in origin-scoped session storage, displays the key, reconciles existing receipts and permits only an explicit exact-payload retry. No automatic retry. Source/deployment replacement can invalidate a pending binding; the old record remains historical and does not authorize new work.
