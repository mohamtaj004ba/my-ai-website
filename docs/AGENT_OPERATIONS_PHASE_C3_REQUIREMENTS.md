## Credential architecture acceptance boundary

Until a reviewed credential broker/key-management provider is configured, connection initiation must truthfully return `configuration-required` rather than redirect to a fabricated OAuth URL, accept pasted secrets in the dashboard, or mark a connection healthy. Redis stores opaque credential references and sanitized metadata, never plaintext tokens.

Recommended provisioning boundary: managed secret vault or envelope encryption with independent KMS IAM, authenticated ciphertext bound to workspace/provider/account/environment/connection/version, server-only access and rotation. No hardcoded/fallback encryption key, no reuse of auth signing keys, and no model/browser decryption interface. [KMS envelope design](https://docs.cloud.google.com/kms/docs/envelope-encryption). Merely encrypting a token with a co-located environment key does not establish managed KMS or an operational connection. Vault/KMS failure, missing scope, expired token and revoked connection all fail closed.

Each call rechecks durable connection revision/revocation, current task/release/fence/cancellation, exact resource/action/role grant, deadline, invocation reservation and rate bound. Recheck before accepting a late result. Revocation cannot recall already transmitted external requests. Retry only explicitly safe non-mutation reads inside the original attempt policy; never resurrect a revoked grant or consume another spending allowance automatically. Provider-side OAuth revocation and local deny are distinct: local denial must be immediate even when provider revocation is unavailable.

## Next predictable failures and required evidence

1. **Scope succeeds but wrong account/environment is connected (high).** Validate provider subject/account/project plus granted scopes, and persist immutable identity. Never equate Google email, Vercel team name, Stripe key shape, or GitHub repository string with authenticated resource ownership.
2. **Connected state mistaken for specialist grant (high).** A service connection does not grant any role authority. Catalogue and policy templates cannot dispatch. Unknown/new roles default-deny; Chief cannot delegate a stronger capability. Per-task authority comes from the existing authenticated task journal, not caller-supplied role/task fields.
3. **Read-only wrapper leaks payload/secrets (high).** Parse bounded allowlisted result fields; never return raw request/response headers, access URLs, logs, stack traces or refresh errors. Emails/web/files are untrusted evidence, not tool instructions. Redact before persistence and model context; hashing private payloads does not make them public.
4. **Cancellation/rate admission is read-check-write (high).** Concurrent/replayed requests must atomically claim allowance in the existing Redis/CAS authority and preserve consumed attempts on uncertain delivery. An in-memory map is not cross-deployment enforcement. Fail closed on store outage; no silent reset on redeploy.
5. **Browser route filtering mistaken for SSRF confinement (high).** Pages may load subresources, workers, sockets and redirects to private addresses. A safe inactive boundary is acceptable; claiming operational isolation requires verified egress/DNS-rebinding protection and process/container limits, not URL regex alone. Preserve the exact unsupported infrastructure prerequisite.
6. **Independent review conflated with connector receipt validity (high).** A genuine GET and intact hash establish provenance, not correctness of a proposal. Preserve unresolved semantics and current separate reviewer limitation. No connector can self-approve or publish from a successful health check.

These are architecture acceptance requirements and credible failure modes, not claims that all are confirmed current defects. Actual gateway/browser implementation review and test evidence must be appended separately before asserting mitigation.
