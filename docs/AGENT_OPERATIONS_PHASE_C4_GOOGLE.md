# Existing Google Workspace consent preparation

This Preview-only extension reuses project `callercore`, existing CallerCore Admin web client and its existing feature-alias `/api/google-oauth-callback`. Application owner `support@callercore.com` and authorized Google mailbox `tj@callercore.com` remain separate identities. No new project, mailbox, client or secret is created. Existing Gmail Inbox records and legacy callback remain separate and untouched.

The authenticated Owner Connections panel prepares incremental `openid`, `email`, `calendar.readonly`, `drive.readonly` and `contacts.readonly` consent. Drive read scope is broad and restricted; owner must review the actual Google consent and applicable internal Workspace/verification requirements. No consent is performed while the owner is away. Docs/Sheets files fall under Drive access; dedicated semantic adapters are not implemented by a scope declaration.

Every request uses the existing session, workspace-owner policy, same-origin API guards and Redis compare-and-audit storage. State is single-use, hashed and bound to owner/workspace, exact immutable deployment, source, release and ten-minute expiry. Only the distinct `agw_` namespace enters the new callback; arrays and ambiguous queries fail before exchange. Fixed Google token/UserInfo endpoints reject redirects and enforce response-byte bounds. Fresh owner and current state are rechecked around provider boundaries. Verified Google subject and required scopes cannot be substituted by same-email identities.

Tokens use the existing server encryption configuration with AES-GCM and owner/workspace/provider/environment/subject additional authenticated data. Tokens never enter model context or UI. Even a fully successful exchange persists only `credential-recorded-unconfirmed`: connected, operational reads, agent access, external writes and paid execution remain false. There is no credential broker, refresh, activation or operational provider-read method in this module. This explicitly contains late storage acknowledgement and cleanup uncertainty; stored credentials are not permission.

The whole callback has a thirty-second bound, each cleanup attempt a separate three-second bound, and the HTTP wrapper a forty-second bound within a sixty-second configured function. Physical cancellation of an in-flight Redis command cannot be guaranteed. Exact-record compensation may be unconfirmed during outages and is reported truthfully. Owner recovery requires the currently visible operation hash and exact revision; it cannot remove a newer reconnect record. Local revoke preserves immutable subject identity and never globally revokes the shared Google grant, which could disrupt the existing Inbox.

The UI performs no automatic provider requests or navigation. It validates the entire fixed Google authorization URL, client, callback, parameter multiplicity, scopes and state before offering an owner link. Runtime/owner/workspace changes invalidate pending UI responses. Full provider consent, refresh, read adapters, resource allowlists and tool activation require later verified work. No operational Workspace connection is claimed from deterministic tests.
