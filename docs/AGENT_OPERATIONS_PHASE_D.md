## Existing implementation inventory and limits

The existing `scripts/agent-operations-draft-workspace.cjs` parent creates a unique temporary directory, copies an approved source file, starts the trusted `agent-operations-draft-child.cjs`, verifies source/output hashes and deletes the temporary directory. Its existing fixed-comment, historical reviewed-calendar and bounded text-replacement profiles remain preserved. Source is treated as text. No `require`, `import`, `eval`, generated script, package script or caller command is run from that source.

The trusted child uses Node filesystem permissions scoped to its implementation modules and one disposable directory; no environment secrets are inherited. Existing parent checks bound input/output bytes, terminate after at most ten seconds, request a 64MB V8 old-space ceiling and verify cleanup plus unchanged authoritative source. Existing proposal preparation revalidates an authenticated caller's authority before and after work. Artifact validation alone is not an authenticated grant.

These measures qualify a closed trusted data transformation only. They do **not** provide a separate kernel, cgroup CPU quota, total resident-memory guarantee, OS process quota, disk quota, complete system-call confinement or a hostile-code escape boundary. Node's old-space flag is not total process memory. A kill of a trusted no-spawn child is not proof of hostile process-tree termination. A package script, test runner, JavaScript syntax import or browser page can execute arbitrary generated code even if its command name is allowlisted. Such operations remain forbidden here.

For new source edits, the existing task controller must retain owner/workspace/source/release/evidence/task/execution/fence identity; resolve allowed files from a server-owned task profile; verify exact complete preimages and unique replacements; bound files, edits, bytes and duration; reject traversal, alternate separators, absolute paths, symlinks, new files, overlapping/ambiguous edits and unsupported source revisions. Protected auth, credential, budget, audit, workflow, dependency and permission files remain excluded. The model cannot choose a profile or expand a manifest. Proposed code stays inert, including any malicious code a content classifier misses.

The controller must recheck cancellation, revocation, emergency stop and authorization revision at admission and before preserving completion. Separate publication, paid inference and generated-code permissions stay false. Persist immutable request/artifact/worker/cleanup receipts in the existing journal; never mutate old evidence or permit a failed upstream stage to become downstream success. Verify original repository hashes after cleanup. Failed cleanup blocks subsequent operations and yields a sanitized incident, not a successful patch.

The initial implementation profile is deliberately limited to the Starter Automations optional-feed entry: the existing handler stays byte-equivalent apart from permitted whitespace, and only the existing entitlement predicate can gate that entry. This is one bounded patch family, not arbitrary autonomous programming. The model can supply the structured explanation, risks, evidence and acceptance mapping; backend validation does not establish that the resulting product behavior is accepted. Artifact flags retain `semanticsUnverified:true` and `executionQualified:false`. Wire parsing must reject duplicate JSON keys before decoding loses their ambiguity; standalone patch-parser tests cannot establish that the actual model-response parser does this.

## Smallest credible dynamic-execution path — proposed, not qualified

Reuse Vercel Sandbox rather than a new agent platform. A source-only Node test qualification can use a managed image without waiting for the separate Playwright browser image. This avoids a custom build/registry dependency for initial pure-JavaScript offline tests; image/runtime identity and exact Node behavior still require qualification. The browser recipe remains pinned to Playwright 1.55.0 Linux AMD64 and is not replaced by this source-only option.

Proposed single qualification: one `iad1` Firecracker microVM, 1vCPU/2GB, maximum five minutes, one controller lease, no parallel session, explicit `persistent:false`, `networkPolicy:'deny-all'`, no exposed ports, drives, snapshots, resume, timeout extension, inherited environment, Git checkout credentials or model/provider tokens. Controller uploads a bounded approved snapshot through the control plane; the VM receives no repository or cloud credential. No `git clone`, package install, runtime download, shell command or network-enabled preparation occurs in the VM. The controller supplies a fixed trusted runner and approved exact tests separately; agent output can modify only the task's source manifest, not runner/tests.

The current provider SDK defaults are unsuitable if accepted implicitly: networking and persistence default open/on. Pin SDK/image and assert returned settings; never use a named existing sandbox with inherited unknown settings. The control-plane credential remains outside the VM. No `sudo` or detached command API is exposed to agents. A non-root dedicated runner account must be verified to lack usable sudo/capabilities, with read-only runner/test files and a distinct writable work directory. Merely passing `sudo:false` does not establish this, since the managed image's account configuration must be inspected.

The microVM protects the host boundary; additional qualified guest confinement is required for the user's filesystem/process/storage requirements. A malicious test must not write outside its task directory or runner-owned output. Before untrusted execution, verify guest UID/permission boundaries, read-only source/test mounting or equivalent trusted setup, dropped privilege, process-tree cleanup, per-test CPU/process/file-size limits and task storage enforcement. Provider default 64GB ephemeral disk is **not** a task storage quota. SDK v3/custom-image disk size is documented; configurable per-task hard quota and process ceiling are not established by these docs. A reviewed guest wrapper may enforce OS resource limits, but its behavior is unqualified until actually tested. No claim that an allowlisted `node --test` alone supplies these controls is permitted.

Qualification success requires: fixed test passes; seeded regression fails as expected; no-network/private-address/DNS probes fail; unauthorized filesystem/protected-test writes fail; subprocess/resource attacks terminate within approved limits; cancellation and emergency stop terminate the entire session; invalid/oversized/symlink outputs are rejected; source/hash/exit/usage/termination receipts bind to the exact task and release; no environment secrets exist; stopped/deleted state is independently observed. Unexpected privilege, network access, missing receipt, cleanup uncertainty or bound failure disables execution. A provider API error is not evidence that termination succeeded. Persist failure and require resolution before another session.

Final logs are bounded and untrusted: no raw environment, headers, customer fixtures or arbitrary stdout in model context; approved paths and sanitized stable codes only. Output patches remain untrusted data after passing tests. No result grants acceptance or publication.
