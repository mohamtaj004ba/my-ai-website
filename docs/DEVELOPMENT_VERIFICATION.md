# Development verification lanes

Source-derived lanes use the actual complete Git comparison, both rename endpoints and protected consumers in both trees. No developer label can lower the lane. Missing history, dirty trees or invalid paths stop selection. Shared/backend/security/Agent Operations/test/tooling/dependency/configuration changes are STRICT. The existing engineering classification is never downgraded.

- FAST: the exact nonruntime documentation allowlist, or explicitly mapped isolated public CSS without active/dependency constructs. Documentation gets targeted policy/release tests and fresh Preview identity, with no new visual acceptance. CSS retains independent QA and affected-page checks.
- STANDARD: explicitly mapped inert public HTML. Active assets, forms, resource attributes, integrations and uncertain dependencies escalate. Existing ordinary backend and dashboard code remains STRICT until dependency impact is proven; no speculative downgrade.
- STRICT: one full test union includes every authoritative contract and policy test exactly once, offline provider guard, source-bound engineering validation, and source/release assertions before and after. Independent Redis, CodeQL, full authenticated Browser QA, QA and Auditor review remain required.

## Batch, qualify and reuse precisely

Batch related corrections before one feature push. Before a configuration refresh, inspect the fresh owner readiness projection and confirm task capacity for both preparation and a fresh live task, shared registry/audit capacity, clean prior authority, unconsumed task-scoped consent, cumulative attempts/budget, exact source/fingerprint, dedicated credential metadata and supported configuration values. Current projections are observations; authoritative admission must revalidate inside the existing CAS and fail closed. A durable configuration dispatch marker must precede every provider mutation. Lost acknowledgments require authoritative readback, never a blind retry.

Reuse a verified configuration and existing cumulative enrollment for later attempts on the same exact immutable deployment, source, fingerprint, assignment, evidence, owner and workspace. Each attempt still needs a fresh task, approval and execution identity; consumed or revoked approvals cannot be reused. No environment edits or redeployment are needed merely to start another eligible attempt on that same snapshot. A new source/deployment does not inherit the old enrollment: current release-bound environment pins and independent Work technical review still require the existing reviewed configuration path. Do not replace those pins with untrusted caller-supplied hashes.

Inspect the automatic full Browser artifact once per qualified source release, including the six visual comparisons and actual screenshots. For a configuration-only snapshot of unchanged qualified source, preserve that source evidence and separately verify the new actual deployment/source/fingerprint, configuration metadata, protected authentication and admission state. Do not claim unchanged full source Browser QA was rerun. Material source, dependency, authentication, UI or rendering changes require the corresponding fresh checks. Documentation checkpoints alone require no application build; batch their publication with a real source release where practical.

Dependency detection is conservative fixed-string analysis, not a proof of arbitrary dynamic imports. New dynamic discovery or shared consumers require STRICT review of the mapping assumptions. Three exact hashed literal-only metadata/allowlist declarations are excluded from consumer detection; any edit invalidates the exception. STANDARD is intentionally narrow. Affected-page hosted behavior must be verified separately before claiming that lane proven.
